0.33.0 - 2026-10-18 #

A minor release on 0.32.1 for one activity ID for every activity, a cmd job's job_id, and the six longest messages shorter; every counter is 0.32.1's (configuration schema 6, registry 31, execution plan 14, daemon IPC 12, command record 4, job manifest and summary 5, plan report 3, credential package 2, scoreboard 4, audit 2, metrics 1, inventory 1), and the module graph is 0.32.1's. A site has something to change where a script lists the scoreboards folder, which holds each activity's claim <ID>.id whatever watch.enabled says; takes a cmd job's job_id for empty or absent; or matches the old words of the six messages. An operator's 0.32.1 daemon, of another build, is drained by the first submission after the upgrade.

  • One activity ID for every activity, never two alike. Every cmd, run, crun, run of a stream, dry run, exercise, and login claims its ID by creating an empty file <ID>.id in the scoreboards folder before anything else, a job that writes files making its job directory under the same ID; a name taken in either moves to the next sequence, and the claim is never handed back. In shared mode the ID is unique on the host, and per operator otherwise: two jobs under --nof in one second, a dry run beside a job, and a login beside a job no longer share an ID, a job's scoreboard no longer replaces a login's, and a second run under --nof through one daemon in the same second runs, where it was refused (idempotency_conflict). The ID's form is unchanged. A claim that cannot be created stops the activity (activity_id_generation_failed); a site that wants no fallback from the shared folder names it in scoreboards and locks the key.
  • A cmd job's job_id is its ID in its summary, its records, its scoreboard, and job list --format json, as a run's is; it was empty in the summary and absent from the records and the scoreboard.
  • watch.max-files counts the scoreboard files alone, not the claims beside them; an empty scoreboard file is a row in error.
  • The six longest messages are shorter, under one rule (DESIGN): the subject by its value, no word that adds nothing, the reason left to the code's description, a remedy last. credkeyref_unresolved, control_path_root_too_long (its length over its limit on lines of their own), setup_tmpfiles_dir_missing, setup_tmpfiles_mismatch, inventory_secret_column, and config_inventory_source_secret_mapping keep their codes and exits; a script that matched their old words changes with them.

0.32.1 - 2026-10-18 #

A patch release on 0.32.0 for the one-letter command words and karvi-audit's wider DEVICE column, which change no record, file, key, or schema; every counter is 0.32.0's (configuration schema 6, registry 31, execution plan 14, daemon IPC 12, command record 4, job manifest and summary 5, plan report 3, credential package 2, scoreboard 4, audit 2, metrics 1, inventory 1), and the module graph is 0.32.0's. A site has something to change only where a script reads karvi-audit's table by position. An operator's 0.32.0 daemon, of another build, is drained by the first submission after the upgrade.

  • One-letter command words: c for command, r for run, l for login, s for stream. Each is an alias, so it matches exactly: karvi c r1 show clock is karvi command and karvi s is karvi stream, where c had been refused as ambiguous (command, config, crun) and s likewise (setup, stream); r and l, which had reached run and login as prefixes, stay theirs whatever word is added. co stays ambiguous, cr stays crun, and se stays setup. The help and karvi(1) list them beside cmd and -.
  • karvi-audit's DEVICE column is 30 cells, from 20, so the extended hostnames of switches, routers, and servers show whole: a canonical name of up to 30 characters whole, a longer one cut with …; COMMAND starts ten cells later, and at a terminal DEVICE is whole and centred from 99 columns (89 before). The lines to a pipe, which a script may read, move with it.

0.32.0 - 2026-10-17 #

A minor release on 0.31.1. The configuration registry moves from 30 to 31, the execution plan from 13 to 14, the command record from 3 to 4, the job manifest and summary from 4 to 5, the plan report from 2 to 3, the scoreboard from 3 to 4, and the audit from 1 to 2; every other counter is 0.31.1's (configuration schema 6, daemon IPC 12, credential package 2, metrics 1, inventory 1), and an operator's 0.31.1 daemon, of another build, is drained by the first submission after the upgrade. karvi-audit is a fourth executable. A site has something to change where a parser reads the audit file, the journal, or the syslog it forwards (the events' names, fields, and line, and the statements, masked, in place of their digests); where a script reads an outcome, a status, or a count by its past-tense word, or the collection's replaced and kept; where a display template names <replaced> or <kept> (refused at load); where a crun.after hook reads KARVI_CRUN_REPLACED or KARVI_CRUN_KEPT; and where a host holds the tab completion file from before (sudo karvi setup tab once more). The module graph is 0.31.1's.

  • Breaking: the audit trail's names, links, and line; audit schema 2. Every audit event is named <kind>.<event>, the kind cmd, run, or crun as job list shows it (action.mode the same word): start and end, once each per job; command, once per device per command, a command never sent included, in place of command_completed; cancel when a cancel is asked, in place of run.cancel_requested; login.start and login.end; and the collection hook's crun.after. An exercise ends in <kind>.end with the outcome exercise, in place of run.exercised. The outcome is in its own field alone, never in the name (login.errored and crun.after.failed are gone), and a start and a cancel carry none. journald's fields: KARVI_JOB_ID on every event of a job, a cmd job's included; KARVI_LOGIN_ID on a login's; KARVI_DEVICE, the device's canonical name, on each command event and a login's; KARVI_OPERATOR, the account the job or the login ran as, on every event; and KARVI_LOGINUSER when the kernel's login UID names another account, the person behind sudo, a job through the daemon taking its client's from the client's process. KARVI_ACTIVITY_ID is gone, and the JSON follows: job_id or login_id in place of activity_id, device.canonical_name in every event (a login's device.name renamed), and loginuser. The message is one line of key=value pairs, karvi.audit=<kind>.<event>, operator, loginuser when it differs, outcome, job or login, device, and command="…", quoted always, in place of karvi audit EVENT outcome=OUTCOME (docs/OPERATIONS.md, "The audit trail"). A site's parser of the audit file, the journal, or the syslog it forwards changes with it.
  • Breaking: the audit records the statements, not their digests. A command event carries its statement as sent, action.command and the line's command="…"; a job's start carries its statements in order, action.commands, which its cancel and end do not repeat. A session-init statement has its own command event, action.command_kind session_init, and stays off the start's list. action.command_sha256, action.command_sha256_array, action.selector_digest, action.plan_digest, policy.config_digest, and the empty command lists of a login's and crun.after's events are gone. An --expect response is never in the audit.
  • The mask: masks and crun.mask; execution plan 14, registry 31. [platform.NAME] masks is a platform's mask list, regular expressions in Go's syntax: in a statement or a line, the text of every capturing group of every match is replaced by <removed>, text two groups cover once, a group that matched nothing left alone. cisco_iosxe (19 patterns), cisco_iosxr (15), cisco_nxos (13), arista_eos (13), and juniper_junos (10) have built-in lists, in force by default; a site's array replaces a list whole, [] turns it off, and a pattern that does not compile or holds no group refuses the configuration, config_platform_mask_invalid (exit 2). Every statement the audit records is masked, in journald and audit.file alike, by the lists of all the job's platforms together; the job's folder keeps the statements as sent. crun.mask (false by default) masks every collection file by its device's own platform's list, a crun's and a run's or command's given --cd, in each line kept and each ! COMMAND marker's statement; --set crun.mask=false keeps one run's files whole unless the site locks the key. The plan carries each target platform's list as platform_masks (docs/COLLECTION.md section 6.1).
  • karvi-audit, the audit trail as a table. A fourth executable beside karvi, karvi-prune, and karvi-askpass, in the package (/usr/bin/karvi-audit, man karvi-audit) and the bundle (install.sh links it from /usr/local/bin). It runs journalctl with the trail's identifier and message ID and shows each event as one row: JOB-ID, OPERATOR (OPERATOR/LOGINUSER under sudo), MODE, EVENT, OUTCOME, DEVICE, and COMMAND at fixed widths, the line cut with … at a terminal, nothing cut to a pipe or a file. -S, -U, -n, -g, -r, and -f are journalctl's, passed as given; -o NAME is the operator or the login user, -d NAME the device, each repeatable. OUTCOME is green, orange, or red by its word; the colour goes to a terminal and through a pipe, never into a file (--nocolor, NO_COLOR). Nothing matched is karvi-audit: no matches on standard error, exit 0; a value journalctl refuses is its own message, exit 1; a usage error exits 2; an event of another audit schema has no row, and one line counts them. It reads no configuration. Tab completes its flags from the same file as karvi's; a host that holds the file from before runs sudo karvi setup tab once more (docs/OPERATIONS.md, "The audit trail").
  • The audit suite. scripts/audit-smoke-test.sh reads the jobs it makes against the fake device back from the host's journal with karvi-audit, each row checked against the event audit.file holds, in the suites' third lane; on a host without journald its journal rows are skipped with the reason.
  • Breaking: an outcome or a status is one present-tense word in every record; command record 4, job manifest and summary 5, scoreboard 4, plan report 3. succeeded is success, completed complete, errored error, failed fail, cancelled cancel, halted halt, and exercised exercise, in the command record's status, the summary's final_status and devices, the scoreboard's status and target states, job list and watch, a login's status, and the audit's outcomes. The counts named after outcomes take their words, device_counts and the scoreboard's counts: done (the devices at an end, job list's DONE, was completed), success, fail, and cancel; total, not_started, incomplete, and in_flight stay. The ping gate's counts in the summary's ping.devices are proceed, proceed_degraded, skip, and capability_unavailable (gated stays), and its display line ends proceed or skip; the plan report's outcome is plan or exercise. The error codes (cancelled, every *_failed), the halt reasons drawn from them, unfinished, and the compound causes (not_attempted_prior_command_failure) stay, so a cancelled record reads status: cancel beside error.code: cancelled. The scoreboard's schema file names its version 4 and declares the targets' bytes and the metrics' in_flight_bytes, which it left out. A record's <status> in the display takes the success role for success and complete, where a succeeded record showed in the error role.
  • Breaking: the collection's replace and keep. The summary's and the scoreboard's collection counts and each device's outcome, and crun.after's details, say replace and keep; the display placeholders are <replace> and <keep>, display.collection.footer's default ! collection=<collection> replace=<replace> keep=<keep>, and a template naming <replaced> or <kept> is refused, display_placeholder_unsupported (exit 2). The hook's environment is KARVI_CRUN_REPLACE and KARVI_CRUN_KEEP, in place of KARVI_CRUN_REPLACED and KARVI_CRUN_KEPT; the shipped examples in /usr/share/karvi/crun/ follow, and a site's copy of one changes with it.

0.31.1 - 2026-10-16 #

A patch release on 0.31.0 for the crun.after hook's bound, which changes no record, file, key, or schema; every counter is 0.31.0's (configuration schema 6, registry 30, execution plan 13, daemon IPC 12, command record 3, job manifest and summary 4, plan report 2, credential package 2, scoreboard 3, audit 1, metrics 1, inventory 1), the module graph is 0.31.0's, and a site has nothing to change. An operator's 0.31.0 daemon, of another build, is drained by the first submission after the upgrade.

  • A crun.after hook's process group is gone when crun returns. At crun.after-timeout, or when the run is interrupted, the hook's process group is sent SIGTERM and, five seconds later, SIGKILL to what is left of it, and crun returns once the group is gone, giving up five seconds after the SIGKILL on a process in uninterruptible sleep. The SIGKILL reached the hook's shell alone, so a child that ignored SIGTERM outlived crun, where docs/COLLECTION.md and crun.after-timeout's documentation said the group was killed. A hook that exits by itself is not followed: what it leaves in its group is its own.
  • The parity suite's hook check looks for the hook's own process group. scripts/native-smoke-test.sh's S33 matched sleep 20 across the host after the hook's bound and ended every match, so another's process failed it, and was ended; it failed the 0.31.0 bundle's verifier once. The hook records its process group, the check looks for that group alone, and the hook's child ignores SIGTERM, so the suite proves the kill.

0.31.0 - 2026-10-16 #

A minor release on 0.30.1. The configuration registry moves from 29 to 30 and the job manifest and summary from 3 to 4; every other counter is 0.30.1's (configuration schema 6, execution plan 13, daemon IPC 12, command record 3, plan report 2, credential package 2, scoreboard 3, audit 1, metrics 1, inventory 1), and an operator's 0.30.1 daemon, of another build, is drained by the first submission after the upgrade. A site has something to change where its configuration names output.files.summary-json (refused at load), where a script took a job folder's summary.json for the job's end (a job has ended when its summary names a final_status), and where a script typed --pl NAME for --platform NAME (--pl is --platform linux). The module graph is 0.30.1's.

  • Breaking: a job's summary is written at its acceptance and at its end; job manifest and summary schema 4. summary.json is written when the job is accepted, after its manifest, naming the job, its plan, its kind, the files it writes, and its devices, with none of the result fields, and written whole again at the job's end. Its presence no longer says the job has ended: a job has ended when its summary names a final_status, which job follow and karvi-prune read. Two fields are new: devices, a list of {name, outcome} in the plan's order, as the scoreboard's targets, the outcome the device_counts category the device is counted in (an exercise's ready or not_ready) and absent at acceptance; and kind, cmd, run, or crun, a job of stream being run and an exercise keeping its kind, beside mode (live or exercise). The manifest moves to 4 with the summary, its content unchanged. karvi-prune takes a folder whose summary names no final status as it took a folder without one, an orphan retired by age alone. The daemon IPC schema stays 12.
  • Breaking: output.files.summary-json is removed; every job folder holds its summary. A configuration naming the key is refused at load, config_unknown_key (exit 2), and the configuration registry moves from 29 to 30. The seven other output.files.* switches false leave a folder holding its summary alone; a job writes no folder only under --nof or output.persist-command = false.
  • karvi job list. The jobs of the output root from their summaries, needing no daemon or credential and making nothing: in shared mode every job of the shared tree, every operator's and a service account's; in individual mode the operator's own. With no option it lists the newest 20 jobs by job ID, whatever their day. --last N (0 every job kept), --failed (the finished jobs whose exit is not 0), --target NAME (run's rule over each job's devices: a glob, repeatable, a leading ! removing; ! values alone are refused, inventory_positive_selector_missing, exit 5), and --operator NAME (repeatable) each judge a job before the count. The table is watch's without ACTV: JOB-ID, TIME (the job's duration), STATUS, OPERATOR (the summary's owner), MODE (the kind), DONE, FAIL, and TARGET, the line fitted to the terminal, each device named whole while it fits and the rest counted as +N, nothing cut to a pipe or a file; under --target one row per matching device, OUTCOME the device's own. An unfinished job shows unfinished, TIME blank, and u in DONE and FAIL, in the warning colour; a folder or a day folder that cannot be read is a ? row, invalid; a list with no row prints (no jobs), exit 0. --format json prints an array of the rows, each the summary's fields with path and operator ({username, uid}) (docs/OPERATIONS.md, "The list of jobs").
  • job follow follows any job from its folder, across the shared tree's members. A job no daemon of the caller's holds, finished or live (a run --no-daemon of another terminal, another member's, a service account's), is followed from its folder: each commands.jsonl record as it is written, then the display's end once its summary names a final status, where only a finished job was read from its folder. In the shared jobs tree a file another member owns is read when its group is the tree's and its mode 0640 or stricter; one of another group is refused run_output_records_unreadable (exit 111), its group over the tree's. While the summary is not final, the job's scoreboard decides: one that is gone, stale by watch.stale-after, or naming the job's end that long ago is job_orphaned (exit 112), where every job without a summary that no daemon held was; under watch.enabled = false another member's live job is job_orphaned at once. A job that keeps no commands.jsonl is followed to its end with one warning, the job's records are not kept (output.files.commands-jsonl is false). A finished job followed from its folder prints the ! ssh accepted new host-key … line, as the daemon's follow does. A job whose day folder cannot be read is run_output_records_unreadable (exit 111), where it was job_unknown (112).
  • watch --all-retained is gone. The option, specified and refused as not available (cli_option_unavailable), is now unknown (cli_option_unknown); job list --last 0 lists every job kept.
  • The job list suite. scripts/job-list-smoke-test.sh runs job list on the jobs of a lab output root made against the fake device (a command, a run with an unreachable device, a crun, an exercise, a killed run, an empty folder, and folders that cannot be read), in the suites' third lane.
  • --pl is --platform linux, --ps is --platform linux_shell. login, command, and run take them beside --pi, --pn, --pr, --pj, --pa, and --pg. --pl is a whole word, so it is no longer a prefix of --platform: a script that typed --pl NAME for --platform NAME now gets linux and NAME as a target or command word (--pla is still --platform).
  • Every HTML page links the repository. The left column of each page of make html, the index too, links https://github.com/robert-patrick-texas/karvi under the name.
  • Tab completion for a shorter name. docs/OPERATIONS.md "Tab completion" and karvi-setup(1) FILES say how a site that links a shorter name such as k to karvi binds it to the same completion (complete -F _karvi k, in a file of its own); nothing in karvi changed.

0.30.0 - 2026-10-13 #

A minor release on 0.29.0. The configuration registry moves from 28 to 29, the execution plan from 12 to 13, and the daemon IPC schema from 11 to 12; every other counter is 0.29.0's (configuration schema 6, command record 3, job manifest and summary 3, plan report 2, credential package 2, scoreboard 3, audit 1, metrics 1, inventory 1). A daemon serves only a client of its own build, and a client that launches its own daemon drains one of another build and starts its own; a service account's daemon runs under the package's system template, set up by karvi-sysutil. A site has something to change where its configuration names daemon.socket (now the directory daemon.sockets), name.default-transform, env-indirection, the sqlite backend type, a key its credential backend's type does not read, or a transform table that does not build (each refused at load); where a credential template holds %s (now text; %operator% is the operator's name) or a CSV cell or a Redis or Vault field begins with env: (now a variable's value); where a Redis or Vault ca-file was meant to add to the host's trust (it is the whole trust); where a script reads daemon status's version: or ipc_schema_version, karvi version's build_time, or colour escapes from a file; where it used the packaged user unit (removed) or installed the bundle by hand (sudo ./scripts/install.sh now); and where it relied on a daemon's stop grace of 120 seconds or its idle hour (daemon.shutdown-grace-seconds 60 and daemon.shutdown-idle-timer 10m now). The module graph is 0.29.0's, golang.org/x/sys now a direct requirement.

  • Breaking: a daemon serves its own build; a client drains another's. A daemon serves a client only when its IPC schema and its build, the last part of the Go build ID its executable carries, equal the client's, where the version and the IPC schema were compared and every release needed karvi daemon restart. Every submission (run, crun, --exercise, --detach, a stream's job) and daemon start drains a daemon of another build at its own schema: holding no job, it exits and the client starts one of its own build in the same invocation (daemon drained version=… build=…, then daemon started); holding jobs, it finishes them and exits after the last, each submission meanwhile refused daemon_draining (exit 112), the daemon's build over the client's. A daemon of a newer schema is refused daemon_incompatible, the schemas stacked. The dry run drains nothing: an idle daemon of another build is the info finding daemon_other_build, a busy one the error daemon_draining. A process that cannot read its own build stops, build_unreadable: daemon serve refuses to start, and a client to submit through a daemon. An interrupt while the client waits for a drained daemon to go or a launched one to answer is cancelled (exit 113), nothing submitted, where it was daemon_start_failed (112).
  • Breaking: daemon status stacks the daemon's values over the client's. daemon_version: over client_version:, daemon_commit: over client_commit:, daemon_ipc_schema: over client_ipc_schema:, and daemon_build: over client_build:, above compatible:, each pair coloured by whether its values agree; version: is now daemon_version:, and the JSON takes the same keys, where it had version and ipc_schema_version.
  • Breaking: IPC schema 12 and execution plan 13. A request carries no client_version or client_pid, and the job header's client holds the client's pid and hostname alone: the daemon checks nothing of the client's. The prepare answer's daemon block names its build and commit, and a client abandons a preparation of another build's daemon before any credential is sent and runs its sequence once more; a second such answer is refused daemon_incompatible.
  • Breaking: a drained daemon exits after its last job, and every stop names its mode. A drained daemon admits no job, finishes those it holds with no time limit, and exits after the last, at once with none (stopping: drained, exit 0). daemon stop --grace drains and waits for the daemon to exit, and --after=DURATION drains, waits up to the limit, and forces; both drain any daemon, at its own schema, where --grace did not drain a daemon of another version. A wait begins with daemon draining: N jobs running; …, which --quiet leaves out, and an interrupt ends the wait alone, the daemon finishing its jobs (daemon_stop_wait_interrupted). Without an option a stop is if_idle, which the daemon, counting its own jobs, refuses while any runs; a stop naming no mode is taken as if_idle.
